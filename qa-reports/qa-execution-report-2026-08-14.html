08

Issues found

Four findings, none of them a security bypass — every unauthorized write attempted during this pass was rejected at the API regardless of what the screen showed.

I-1 · Medium

Patient name edits don't propagate to related records

Appointments, OPD, Billing, Lab, Prescriptions, and Radiology each store their own copy of the patient's name at the moment the record is created, and nothing updates that copy when the patient is later renamed (see Section 04). For a bill or a lab report, freezing the name as of that visit is arguably correct — you don't want history rewriting itself. For Appointments, OPD, and Prescriptions it's more likely to read as a bug to front-desk staff searching by current name.

Where appointments-service.ts, billing-service.ts, lab-service.ts and siblings · Fix either cascade the rename into denormalized rows, or join against the live patient name at read time
I-2 · Low

Write buttons render regardless of role permission on 10 pages

Billing, Inventory, OT (list, new, and detail), Pharmacy, Beds & Wards, Records, Finance, Staff, the main Prescriptions list, and the Lab/Billing detail-page actions all show their Add / Edit / Delete / status-change controls to every role, unlike the pages already gated this session (OPD, IPD, Patients, Appointments, Doctors, Lab, Radiology, Ambulance, TPA, Blood Bank). Confirmed with Head Nurse against OT, Billing, and Staff — the button is visible but every submit still comes back 403. It's a confusing UI, not an access hole.

Where the 10 page files listed above, none of which call useAuth().can(...) · Fix apply the same can(resource,"write") gating pattern used elsewhere
I-3 · Low

Reports dashboard shows static KPI values

Most tiles on /reports (Total Revenue ₹4.8L, +14%, New Registrations 312, …) are hardcoded and never change with real data; only the header stat pill is bound to the live report. Anyone using this page to check current numbers is looking at fixed placeholder figures.

Where src/app/(dashboard)/reports/page.tsx · Fix bind each tile to report.kpis the way the header pill already is
I-4 · Low

No live sync between open sessions

Restated from Section 05: shared views such as the OPD queue or bed board don't update for a second viewer until they navigate or reload. Acceptable for the current single-terminal-per-desk usage pattern; worth a polling or WebSocket layer if multiple staff start watching the same board simultaneously.

Where architectural — no realtime transport in the stack · Fix short-interval polling on the highest-traffic boards would be the cheapest first step

10

QA conclusion

Access control is sound: the role matrix built up over this project's many role-permission requests was verified role by role, and in every negative test attempted — a Doctor posting to Billing, a Head Nurse posting to OT, a Driver reading Staff — the server rejected the request regardless of what the interface displayed. That held true even for the pages flagged in I-2, which is the reason those are graded low severity rather than a security finding.

The one functional defect (I-1) is narrow and well understood: six services write a name snapshot on create and nothing updates it afterward. It's a straightforward fix once a decision is made about which modules should show current identity versus a point-in-time record.

No blocking issues were found. The platform is stable enough for continued use in this environment, with I-1 through I-4 tracked as follow-up work rather than release blockers.
